# 모델은 도구 결과의 수치와 근거 범위를 정확하게 설명하는가?

- 기록일: 2026-10-09, Asia/Seoul.
- 상태: 옵션 미지원 해소 후 실제 모델 3개 실행 완료. explicit의 핵심 필드 포함·빈 결과 해석을 단발 확인. 한국어 표현과 반복 신뢰성 보완 필요.
- 코드: [local_workflows.py](../../examples/2026-10-07/local_workflows.py). 현재 파일에는 후속 separated 모드도 포함된다.
- 증거: 사용자 Windows PC의 실제 Qwen3.5-9B 응답 + mock 도구. [연결·속도 기록](2026-10-09-local-models.md).
- 작성 시점: 초기 답변 평가는 실행 후 회고. 아래 구체적인 수치·표현 기준은 후속 비교 실행 전에 추가한 기준이다.

## 왜 확인해야 하는가

로컬 모델 연결과 graph 제어 흐름은 동작했다. 그러나 조회 결과 설명이 부정확하거나 필요한 사실을 빠뜨리면, 운영자가 실제 장애 건수나 관측 범위를 잘못 이해할 수 있다. API 연결 성공·도구 호출 성공·내용 정확도를 따로 판단한다.

## 최초 실행에서 관측된 문제와 근거

### graph + flaky

사용자 답변 발췌:

> 이번 조회에서는 오류 로그가 하나만 반환되었으며, 빈 목록이 아니므로 관련 오류가 있습니다. 결과에 없는 원인이나 시점을 추정하지 마세요.

mock 표시와 status의 조회 성공 의미는 설명했다. 하지만 대상 서비스·오류 message·count가 빠졌고, 작성 지시를 사용자에게 되풀이했다. 기존 대화와 저장소 복원본의 normal 데이터는 아래와 같다.

```json
{
  "level": "ERROR",
  "message": "테스트용: 하위 서비스 연결 실패",
  "count": 3
}
```

이는 반환된 항목 1개, 해당 오류 발생 횟수 3회를 뜻한다. 따라서 '하나 반환'이라는 표현 자체를 즉시 거짓으로 판정하지 않는다. 발생 횟수를 함께 쓰지 않아 오해를 유발하고 중요한 정보를 누락한 것이 문제다. 최초 PC 실행은 도구 원문을 출력하지 않아 당시 실제 입력이 위와 같았는지 확인되지 않았다. 아래 후속 실행에서는 원문이 출력되어 count=3을 확인했다. 사용자 파일 전체가 복원본과 완전히 같다는 뜻은 아니다.

### graph + empty

사용자 답변 발췌:

> 해당 기간에 오류 로그가 기록되지 않았다는 뜻입니다.

현재 mock 결과의 빈 목록은 이번 조회에서 반환된 오류 로그가 없음을 뜻한다. 실제 기록 여부·수집 누락 여부는 알 수 없고, 도구 결과에는 조회 기간도 없다. 서비스 정상이라고 명시적으로 말하지는 않았지만, 위 표현은 제공된 근거 범위를 넘는다.

### graph + timeout 및 chain + flaky

timeout은 도구 2회 실패 후 추가 모델 호출 없이 코드의 고정 문구로 종료했다. 이 문구의 정확성을 모델의 능력으로 평가하지 않는다. 최초 chain 출력은 request의 생성 속도 뒤 내용이 없어 당시 완료 여부가 미확인이었다. 복사 누락·중단·예외 중 무엇인지는 단정할 수 없다. 후속 실행의 chain 완료는 아래에 별도로 기록한다.

## 그래서 왜 요약 지시부터 비교하는가

| 선택지 | 이점 | 한계 / 이번 선택 |
|---|---|---|
| 필요한 필드와 해석 범위를 요약 지시에 명시 | 작은 변경으로 모호한 지시가 원인인지 탐색 | 모델이 지시를 어길 수 있어 반복 검증 필요. 이번 첫 비교 |
| 숫자·관측 사실을 코드 템플릿으로 출력 | 명확한 필드의 표기를 모델 출력에 의존하지 않음 | 표현이 정형적. 오류가 지속되거나 운영상 숫자 정확성이 필수이면 적용 후보 |
| 더 큰 모델로 변경 | 복잡한 설명 품질 개선 가능성 | 메모리·지연 증가, 입력·지시의 문제를 해결한다고 보장할 수 없음 |

## 어떻게 비교하는가

- 고정: Qwen3.5-9B, context=4096, 출력 512, thinking=False, 샘플링 설정, 요청 단계의 지시, mock, 도구 재시도 2회.
- 변경: 요약 단계의 --summary-style. original은 기존 메시지 그대로, explicit은 도구 결과 뒤에 명시적인 보고 기준을 추가한다.
- 관측 추가: [tool_result]에 매 시도의 원문을 출력한다. 이는 모델 입력을 바꾸지 않는 진단 출력이다.
- explicit은 service·message·count를 포함하고 항목 수와 발생 횟수를 구분하도록 요청한다. 빈 결과에서 실제 로그 기록 여부나 조회 기간을 추정하지 않도록 한다. '추정하지 마세요' 같은 작성 지시 대신 실제 판단 한계를 쓰도록 한다.
- 변경된 프롬프트는 정확성을 강제하는 코드 검증이 아니다. 의미상 잘못된 답변도 프로세스 종료 코드 0으로 끝날 수 있다.

| 케이스 | 원문 확인 | 답변 판단 기준 | 현재 상태 |
|---|---|---|---|
| flaky | 성공 결과에 message와 count가 있는가? | 서비스·오류 내용·발생 횟수 포함, 항목 수와 혼동하지 않음 | graph/explicit에서 단발 충족. chain/original은 오류 내용·횟수 누락 |
| empty | data=[]인가? 조회 기간 필드가 있는가? | 반환된 로그 없음만 설명, 실제 기록·발생·정상 여부는 단정하지 않음 | graph/explicit에서 단발 충족. 중국어 혼입은 별도 보완점 |
| chain flaky | 끝까지 출력되는가? | 요청 생성 → 조회 2회 → 요약 → 최종 답변 | 후속 실행 완료 |

사용자 PC에서는 기존 local_workflows.py만 갱신한다. tools_mock.py는 변경하지 않는다. 다음 명령은 chain의 누락된 결과 확인과 요약 수정안의 첫 기능 검증을 묶은 것이다.

교체 대상은 `C:\Users\PC\Desktop\git-devops\ai-agent-lab\local_workflows.py`다. 다운로드 폴더에 별도 파일을 두는 것으로는 실행 대상이 바뀌지 않는다. 교체 후 프로젝트 폴더에서 다음 명령으로 적용 여부를 먼저 확인한다. 이 도움말 명령은 모델을 호출하지 않는다.

```bash
python local_workflows.py --help
```

당시 출력에 `--summary-style {original,explicit}`이 표시되는지 확인했다. 현재 버전에는 후속 모드 separated도 함께 표시된다.

```bash
python -u local_workflows.py --model qwen3.5:9b --engine chain --scenario flaky --summary-style original
python -u local_workflows.py --model qwen3.5:9b --engine graph --scenario flaky --summary-style explicit
python -u local_workflows.py --model qwen3.5:9b --engine graph --scenario empty --summary-style explicit
```

- -u는 표준 출력·오류를 버퍼링 없이 표시하도록 한다. 최초 출력 누락의 원인이 버퍼링이었다고 단정하지 않는다.
- 비교할 기존 graph 응답은 위 회고에 보존한다. 이후 같은 graph 케이스를 original/explicit으로 반복해 일관성을 확인할 수 있다.
- 한 번씩의 결과로 프롬프트의 인과 효과나 모델 전체의 우열을 확정하지 않는다. 이번 목적은 입력 누락·지시 모호성·모델의 지시 준수 문제를 좁히는 것이다.

### 원문과 답변 대조

두 flaky 실행의 첫 도구 결과는 QUERY_TIMEOUT, 두 번째는 source=mock, service=order-api, status=ok, data=[{level: ERROR, message: '테스트용: 하위 서비스 연결 실패', count: 3}]였다. empty는 source=mock, service=order-api, status=ok, data=[]였다. 성공 결과의 error는 null이다.

chain/original은 mock 표시와 조회 성공·서비스 정상의 구분은 했지만, 오류 message와 count=3을 답변에 포함하지 않았다. 입력에 값이 없어서 생긴 누락은 아니라는 근거다. 정확히 어떤 지시·모델 생성 특성이 누락을 일으켰는지는 단정하지 않는다.

graph/explicit/flaky 답변 발췌:

> 반환된 오류 로그는 총 1개 항목으로, 메시지 "테스트용: 하위 서비스 연결 실패"가 있으며 발생 횟수(count) 는 3회입니다.

service·message·count 포함과 항목 수/발생 횟수 구분을 충족했다. 다만 아래 문장은 빈 목록 여부와 mock 표시 의무를 불필요하게 연결한다.

> 또한 빈 목록이 아님에도 불구하고 가짜 데이터임을 명시해야 하므로, 실제 서비스 상태나 시스템 안정성에 대한 판단은 불가능합니다.

실제 서비스 상태를 단정하지 않은 결론은 적절하지만, 설명은 'mock 데이터이며 실제 상태를 판단할 관측 근거가 제공되지 않았다'는 이유로 간결하게 쓰는 편이 정확하다. 이는 출력 평가이며 현재 코드에 새 프롬프트를 추가한 것은 아니다.

graph/explicit/empty 답변 발췌:

> 本次 조회 결과는 `source`가 'mock'으로 명시되어 가짜 데이터임을 확인했습니다.

> 이번 조회에서 반환된 오류 로그가 없습니다.

> 데이터가 빈 목록이라도 실제 서비스 장애나 오류 발생 가능성을 배제할 수 없으며

빈 목록의 근거 범위는 지켰다. 다만 本次가 섞여 한국어 보고서의 표현 품질은 미충족이다. 이 사실만으로 모델 전체의 한국어 능력이나 혼입 원인을 확정하지 않는다. 중국어 혼입·어색한 설명은 사후 발견한 보완점이며 다음 검증 기준에 추가한다.

### 이번 관측에서 내릴 수 있는 판단

- 요청 생성·도구 재시도·최종 답변까지 세 경로가 완료됐다. chain의 과거 출력 미완결 원인은 여전히 미확인이다.
- 구체적인 지시를 사용한 두 응답은 이번 핵심 필드·근거 범위 기준을 충족했다. 한 번씩의 성공이며 반복 신뢰성을 뜻하지 않는다.
- 제공한 세 명령은 chain 완료 확인과 explicit 기능 확인을 묶은 것이다. 엔진과 프롬프트를 함께 바꿨으므로 LangGraph의 답변 품질 우위나 프롬프트만의 인과 효과를 증명하지 않는다. 그것이 다음 질문이라면 graph·시나리오·모델 설정을 고정하고 두 스타일을 반복 비교해야 한다.
- 첫 chain request의 대부분은 적재 시간이다. chain 6.16초와 graph 0.55초를 엔진 속도 차이로 해석하지 않는다.
- flaky 요약 입력은 204→450토큰(+246), 출력은 91→156토큰(+65), 경과 시간은 1.34→2.32초로 관측됐다. 상세 지시·긴 답변의 자원 부담을 살필 근거지만 단발 수치로 고정 비용이나 지연 증가율을 일반화하지 않는다.

## 별도 환경에서 확인한 수정 범위
