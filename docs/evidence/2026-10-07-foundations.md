# 2026-10-07 실습 회고: 어떤 작업을 다시 실행하고 어디서 멈추는가?

## 기록의 범위

실행일: 2026-10-07. 구조 정리일: 2026-10-08. 상태: 일부 미검증. 기준: [학습 원칙](../learning-principles.md).

사용자가 공유한 Windows Git Bash 실행 출력을 근거로 작성했다. 아래 결과는 사용자 PC에서 실행한 코드의 결과이며, `examples/2026-10-07/` 복원본을 실제 API로 재실행한 결과가 아니다.

이 문서는 일일 실습 회고이며 재시도 실험을 중심 사례로 정리한다. 아래 선택 근거와 가설 표는 당시 안내와 결과를 **사후에 구조화한 것**이다. 학습자가 실행 전에 모두 판단하거나 이해했다고 주장하지 않는다. 새로운 API 실행은 하지 않았다. 정확한 패키지 버전은 미수집이다.

## 1. 왜 이 실험까지 왔는가

먼저 모델 연결과 도구 실행을 구분하고, 같은 기능을 LangChain 구성요소와 LangGraph로 구성했다. 그다음 실패 시 재조회와 종료를 어떻게 통제하는지 확인했다.

| 앞선 작업 | 확인하려던 질문 | 공유된 결과 |
|---|---|---|
| 가상환경 | 어느 Python으로 실행하는가? 폴더 이동만으로 활성화되는가? | Python 3.11.5, 명시적 activate 필요 |
| Gemini 첫 호출 | 실제 모델 API에 요청·응답이 연결되는가? | 1.14초, 입력 21·출력 9·총 30토큰, STOP |
| mock 도구 | 결과 없음과 조회 실패를 구분하는가? | normal / empty / timeout 반환 확인 |
| SDK 도구 연결 | 모델의 요청과 실제 함수 실행은 어떻게 이어지는가? | ANY 도구 요청 → Python 실행 → 결과 설명 확인 |
| 기본 비교 | 같은 부품을 Python 순서문과 그래프로 연결하면 동작이 같은가? | 두 방식 × normal / empty / timeout의 6개 경로 확인 |

초기 단계의 전체 원문 로그는 이 문서에 첨부하지 않았다. 코드와 재현 방법은 [예제 안내](../../examples/2026-10-07/README.md), 범위별 진행 상태는 [진행 기록](../progress.md)을 따른다.

**문제:** 한 번의 조회 실패로 바로 종료하면 일시적 오류에서 복구할 기회를 놓칠 수 있다. 반대로 계속 반복하면 자원·시간을 낭비하고 종료를 보장하지 못한다.

**핵심 질문:** 이미 정한 조회 요청을 재사용하면서, 일시 실패 후에는 다음 단계로 진행하고 계속 실패하면 정한 횟수에서 멈출 수 있는가?

이 질문은 프레임워크의 우열보다 재시도 범위·상태·종료 조건을 이해하기 위한 것이다.

## 2. 그래서 왜 이 방법을 선택했는가

아래는 안내자가 제시한 이번 구현의 근거다. 학습자가 독자적으로 내린 결정으로 기록하지 않는다.

| 선택지 | 장점 또는 적합한 조건 | 한계 | 이번 선택 |
|---|---|---|---|
| 실패 즉시 종료 | 빠른 실패 보고가 필요한 경우, 추가 요청 최소화 | 일시 오류의 복구 기회를 활용하지 못함 | 기존 비교 버전에서 관찰 |
| 모델 요청 생성부터 전체 재실행 | 조사 대상·계획을 새로 판단해야 할 때 검토 | 같은 조회에서는 불필요한 모델 호출, 다른 요청이 생성될 수 있음 | 사용하지 않음 |
| 같은 요청으로 도구만 제한 재시도 | 조회 대상과 조건이 그대로인 일시 실패 | 대기·총 시간 제한 등 별도 정책 필요 | 이번 실습에서 사용 |
| 무제한 재시도 | 복구 시점을 모르는 동안 계속 기다림 | 종료·시간·자원 상한을 보장하지 못함 | 사용하지 않음 |

- **도구만 재실행:** 대상과 요청이 바뀌지 않았으므로 요청 생성 모델을 다시 호출할 필요가 없다.
- **최대 2회:** 최초 1회 + 재시도 1회로 복구와 중단을 작게 비교한다. 운영 최적값을 측정한 것은 아니다.
- **QUERY_TIMEOUT만 대상:** 일시 실패로 취급할 오류를 명시한다. 권한 오류 등까지 무조건 반복하지 않는다. 실제 환경에서는 timeout도 원인에 따라 반복으로 해결되지 않을 수 있다.
- **mock 유지:** 외부 로그 서버 변수 없이 반복과 종료를 관찰하기 위해서다. 모델 API는 실제로 호출했으므로 외부 의존성을 모두 제거한 실험은 아니다.
- **두 실행 방식 비교:** 부품과 정책을 고정하고 while 반복문과 그래프의 되돌아가는 연결을 비교한다. 더 좋은 모델 답변을 얻는 실험이 아니다.

**선택을 바꿀 조건:** 새로운 증거로 조사 대상이 달라지면 재계획을 검토한다. 실제 조회에 연결하면 대기 간격·전체 제한 시간을 설계한다. 중복 실행으로 부작용이 생기는 쓰기 작업에는 이 조회 정책을 그대로 적용하지 않는다.

## 3. 어떻게 확인할 것인가 — 사후 정리한 검증 구조

- 가설: 저장한 요청을 재사용하고 시도 횟수를 상태로 전달하면, 두 방식 모두 flaky는 두 번째에 성공하고 timeout은 두 번째 실패 후 종료한다.
- 바꾼 조건: engine(chain / graph), scenario(flaky / timeout).
- 고정한 조건: 서비스 order-api, 도구 설명·입력 형식, 최대 시도 2회, 결과 형식, 분기 함수.
- 관측 위치: request / execute / summarize / unavailable 출력과 총 조회 시도.
- 제외한 범위: 실제 서버 복구율, 실제 네트워크 예외 변환, SDK 내부 통신 시도 수, 장기 신뢰성.

| 케이스 | 예상 관측 | 판단 기준 |
|---|---|---|
| flaky | request 1회, execute 실패→성공, summarize | 모델 요청을 다시 생성하지 않고 도구 두 번째 시도 후 설명 |
| timeout | request 1회, execute 실패→실패, unavailable | 세 번째 도구 실행과 summarize 없이 종료 |
| request에서 모델 API 실패 | 도구 실행 전 중단 | 도구 재시도 가설의 성공·실패가 아니라 목표 단계 미도달 |

## 4. 실행과 실제 결과

- `tools_mock.py`: get_recent_errors를 제공한다. 모델 없이도 결과를 확인할 수 있다.
- `retry_workflows.py`: 모델 요청·도구 실행·재시도 분기·최종 설명을 연결한다.
- 주요 상태: messages, tool_call, tool_message, result, attempts, answer.
- 중요한 설정: `MAX_ATTEMPTS=2`는 도구 실행 상한, `max_retries=0`은 모델 설정이며 적용 범위가 다르다. SDK 내부 실제 시도 수는 설치 버전 확인 없이 단정하지 않는다.

```bash
python retry_workflows.py --engine chain --scenario flaky
python retry_workflows.py --engine graph --scenario flaky
python retry_workflows.py --engine chain --scenario timeout
python retry_workflows.py --engine graph --scenario timeout
```

| 실행 | 사용자 출력에서 확인한 결과 | 판정 |
|---|---|---|
| chain + flaky | 첫 모델 요청에서 Gemini 503 UNAVAILABLE, 도구 실행에 도달하지 못함 | 복구 경로 미검증 |
| graph + flaky | 첫 도구 조회 QUERY_TIMEOUT, 두 번째 조회 ok, 최종 설명 출력 | 복구 경로 확인 |
| chain + timeout | QUERY_TIMEOUT 두 번, unavailable로 종료 | 상한 종료 확인 |
| graph + timeout | QUERY_TIMEOUT 두 번, unavailable로 종료 | 상한 종료 확인 |

`chain + flaky` 재실행에서도 같은 위치의 503이 발생했다. 서버 응답은 모델의 높은 수요를 이유로 제시했다. 이후 두 timeout 실행은 첫 모델 요청을 통과했다. 이 결과로 chain과 graph의 모델 안정성 차이를 판단할 수 없다.

성공한 graph + flaky 실행의 핵심 출력:

```text
[request] 모델 호출: 조회 요청 생성
[execute] 시도 1/2, status=error
  오류: QUERY_TIMEOUT
[execute] 시도 2/2, status=ok
[summarize] 모델 호출: 최종 조회 결과 설명
[총 조회 시도] 2회
```

두 timeout 실행에서 공통으로 확인한 핵심 출력:

```text
[execute] 시도 1/2, status=error
  오류: QUERY_TIMEOUT
[execute] 시도 2/2, status=error
  오류: QUERY_TIMEOUT
[unavailable] 추가 모델 호출 없이 종료
[총 조회 시도] 2회
```

## 5. 그래서 무엇을 알게 됐는가

- MAX_ATTEMPTS=2는 최초 시도를 포함한 도구 실행 상한이다.
- flaky는 첫 조회 실패와 두 번째 성공을 의도적으로 만든 mock 시나리오다. 실제 서버 복구를 검증한 것이 아니다.
- 모델 API 실패와 도구 조회 실패는 발생 위치와 재시도 대상이 다르다.
- status=ok는 조회 성공이며 서비스 정상 판정이 아니다. mock 로그에는 하위 서비스 연결 실패 3건이 반환되었다.
- timeout 종료에서는 로그를 확보하지 못했으므로 서비스 상태를 판단하지 않는다.
- chain은 LangChain 구성요소와 일반 Python 제어문을 사용하는 예제이며 create_agent와 LangGraph를 비교한 것이 아니다.

가설에 대한 판단: graph + flaky와 두 timeout 경로는 관찰 결과가 예상에 부합했다. chain + flaky는 모델 503으로 목표 단계에 도달하지 않아 판단을 보류한다. 이를 “Python 반복문은 실패하고 LangGraph는 더 안정적”이라고 해석할 수 없다.

실무에 옮길 수 있는 판단 기준은 **재시도는 프로그램 전체가 아니라 실패한 작업의 범위와 성격을 먼저 보고 설계한다**는 것이다. 이를 사용자가 자기 말로 설명했는지는 별도 확인 대상이다.

## 6. 진행 중 발생한 오류에서 배운 것

| 관측 | 원인 위치 | 조치·학습 포인트 |
|---|---|---|
| BaseMessage ImportError | langchain.messages import | langchain_core.messages로 수정. 패키지 설치 여부와 공개 경로를 구분 |
| tools_mock.py에 새 코드 입력 | 파일 역할·수정 대상 혼동 | 원래 도구를 복원하고 새 실행 파일을 분리. 새 파일/수정 파일을 먼저 명시 |
| No module named retry_workflows | 프로젝트 폴더에 retry 파일 없음 | pwd와 ls로 확인 후 생성. 패키지 재설치 문제가 아님 |
| Gemini 503 | request_model.invoke | 모델의 높은 수요를 보고한 응답. 도구 mock 실패와 별도 처리 필요 |

파일을 찾은 뒤에는 실제 모델 호출까지 진행했다. import 확인은 main 가드가 있는 이 파일에서 모델 호출 없이 로딩을 검사한 것이며, 모든 import가 부작용이 없다는 뜻은 아니다.

## 7. 복원본의 검토 상태

Python 파일 5개의 AST 문법 검사와 기존 변경 사항의 공백 오류 검사를 통과했다. 일반적인 API 키·개인 키 패턴 검사에서 일치 항목이 없었다. 실제 API 통합 실행, 사용자 PC 원본과의 일치 여부, 의존성 버전 재현성은 확인하지 않았다.

## 8. 남은 질문과 다음 행동

| 남은 질문 | 다음 행동 | 필요한 이유 |
|---|---|---|
| 어떤 코드·버전으로 실행했는가? | PC 원본과 복원본 대조, 버전 기록 | 재현 범위를 명확히 하기 위해 |
| 모델 503은 어디서 얼마나 재시도할 것인가? | 모델 API 정책을 도구 정책과 분리 설계 | 재시도가 여러 층에서 중첩되는 일을 통제하기 위해 |
| chain의 복구 경로도 예상대로인가? | 해당 경로 검증 또는 별도의 모델 대역 테스트 | 현재 출력으로 확인하지 못한 부분을 해소하기 위해 |

모델 대역 테스트를 한다면 실제 API 통합 성공으로 바꿔 기록하지 않는다. 이 기록과 학습 원칙의 정리안은 2026-10-09 사용자 승인에 따라 커밋 대상으로 확정했다. 이후 새 실습 결과는 별도로 기록한다.
