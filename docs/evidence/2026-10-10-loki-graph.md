# Loki 조회 결과가 LangGraph의 사실 출력과 모델 설명까지 보존되는가?

- 실행 / 기록일: 2026-10-10, Asia/Seoul.
- 상태: 구현과 HTTP 대역 검증, 사용자 PC의 실제 Loki + Qwen + LangGraph 일반 조회 통합 확인. 이번 사례의 최소 관측 기준을 충족해 확인 종료.
- 코드: [local_workflows.py](../../examples/2026-10-07/local_workflows.py), [새 연결 테스트](../../examples/2026-10-07/test_loki_workflows.py), [조회 함수](../../examples/2026-10-10/loki_query.py). 실제 관측과 별도 환경의 검증을 아래에서 구분한다.
- 출처: 별도 Linux Python 3.12.14 환경의 실제 LangGraph·Ollama SDK + HTTP 대역, 17:16 KST에 사용자가 공유한 실제 PC 통합 출력. 두 출처의 결과를 아래에서 구분한다.
- 작성 시점: 기준·예상은 사용자 PC 통합 실행 전에 작성했다. 관측 결과는 후속 공유 출력으로 갱신했다. 최소 증거 기준은 사용자의 재실험 필요성 지적을 반영해 추가했다.

## 1. 결정할 질문과 기존 근거

핵심 질문은 **실제 조회 함수의 결과를 그래프가 전달하고, 코드가 필수 사실을 보존하며, 모델은 별도 설명을 하는가?**이다. 결과가 일치하면 다음 요구로 넘어간다. 불일치하면 도구 호출·상태 전달·사실 변환·모델 지시 중 문제가 발생한 위치를 수정한다.

기존 근거는 [Loki 조회 기록](2026-10-10-loki-query.md)이다. 같은 요청 ID로 curl과 Python이 동일한 info 로그 1줄을 반환했고 errors-only 조건은 성공한 빈 결과를 반환했다. 앱 로그 생성·Loki 수집·Python HTTP 조회를 다시 증명하기 위한 장애 주입은 이번 선행 조건으로 두지 않는다.

새로 바뀐 조건은 LangChain 도구의 내부 호출, LangGraph 상태 전달, Loki용 사실 출력과 설명 지시다. 이미 확인한 시간 범위·요청 ID·원문을 재사용해 새 연결만 대조한다.

## 2. 선택과 이유

| 선택 | 근거와 한계 |
|---|---|
| 기존 local_workflows.py에 --source mock/loki 추가 | 기존 프레임워크·모델·노드 구성을 재사용한다. mock의 시나리오와 실제 조회 조건을 구분해야 한다. |
| Loki 도구 이름 get_logs, --errors-only 선택 | 기존에 확보한 info 로그를 통합 비교 기준으로 사용할 수 있다. 오류 전용 이름으로 일반 로그를 가져오지 않는다. |
| Loki는 separated 보고 방식 사용 | 원문·범위·줄 수는 코드가 표시하고 모델은 한계·다음 확인을 맡는다. 설명의 의미상 정확성은 자동 검증되지 않는다. |
| 범위·필터·상한은 CLI, 모델 인자는 service 하나 | 이번에는 도구 요청과 검증 경계를 확인한다. 자유로운 자연어 시간 추출과 다중 서비스 조사는 후속 요구다. |
| 상대 조회 기간을 모델 호출 전 고정 | 같은 요청의 재시도에서 범위가 이동하지 않는다. 새 사건을 재조사하려면 새 조회 조건을 만들어야 한다. |
| 기존 timeout 최대 2회 정책 유지 | 새 연결에 재시도 정책 변경까지 동시에 섞지 않는다. HTTP 503은 현재 재시도하지 않고 조회 실패로 종료한다. |

조회가 코드와 순서를 따라 수행되는 현재 구성은 정해진 workflow에 가깝다. 모델이 조사 대상을 자유롭게 재계획하는 구조까지 구현했다고 주장하지 않는다. [LangGraph 공식 설명](https://docs.langchain.com/oss/python/langgraph/workflows-agents)은 workflow의 정해진 코드 경로와 agent의 동적 실행을 구분한다.

## 3. 최소 관측과 종료 기준

사용자 PC에서는 아래 **일반 조회 통합 실행 한 번**으로 시작한다. 같은 시간 범위와 요청 ID를 사용한다.

| 위치 | 최소 증거 | 결과에 따른 행동 |
|---|---|---|
| request | get_logs, service=order-api | 다른 도구/대상이면 요청 지시·검증을 확인. 검증 실패 시 Loki 조회 금지 |
| execute | source=loki, status=ok, returned_count=1, 기존 원문/시각/요청 ID | 기존 근거와 다르면 도구 설정·결과 전달 위치 확인 |
| 코드 사실 | 조회 범위·조건·원문·로그 줄 수 1, level=info | 오류 발생 횟수로 바꾸거나 info를 오류로 표기하면 출력 코드 수정 |
| 모델 설명 | source·info 로그·현재 조회 범위와 모순되지 않는 설명 | 조회가 맞으면 설명 지시/응답을 검토. 로그 생성 실험을 다시 하지 않음 |

위 관측이 일치하면 현재 통합 확인을 종료한다. 의미상 잘못된 설명은 explanation_status=ok여도 완료로 판정하지 않는다. 이 상태는 텍스트 생성 완료만 뜻한다.

동일 실행의 반복은 관련 코드·계약·모델 설정 변경, 새 모순, 기존 범위 밖 요구, 사전 반복 평가 계획이 있을 때만 한다. 성능 비교나 반복 신뢰성 평가를 이번 단발 통합 확인에 포함하지 않는다.

## 4. 구현과 검증

변경 위치:

- make_loki_tool 내부에서 query_logs를 호출하고 execute_node가 ToolMessage의 결과를 state.result에 보관한다.
- request_node는 도구 이름·인자 집합·요청 서비스가 설정과 일치하는지 검증한다.
- validate_tool_result는 Loki 조회 메타데이터, 반환 수/상한 표시, 각 로그의 서비스 라벨을 검사한다.
- render_loki_facts는 mock 집계와 구분해 Loki 원문·시각·조회 조건·줄 수를 표시한다. count를 새로 만들지 않는다.
- summarize_node의 separated 경로는 전체 도구 결과를 설명 모델에 전달한다. 사실 문자열은 모델 응답으로 다시 쓰지 않는다.
- Loki 조회 실패의 CLI 종료 코드는 2다. 설명은 생략하고 조회 실패 사실을 출력한다.
- prepare_query는 통신 없이 입력을 검사하고 시간 범위를 고정한다. 입력 오류를 모델 호출 전에 확인한다.

별도 환경: Python 3.12.14, langchain 1.4.4, langchain-core 1.6.9, langgraph 1.2.14, langchain-ollama 1.1.0, ollama 0.6.3, httpx 0.28.1. 이 환경의 프록시 관련 SDK import를 위해 socksio 1.0.0을 추가했다. 사용자 PC의 패키지 업데이트를 요구하지 않는다. 전체 의존성 lock은 아니다.

```bash
python -m unittest discover -s examples/2026-10-07 -p 'test_*workflows.py' -v
python -m unittest discover -s examples/2026-10-10 -p 'test_*.py' -v
```

첫 명령: 기존 mock 회귀 검사 9개와 새 연결 검사 5개, 총 14개 PASS. 두 번째: 조회 함수의 입력·응답 경계 검사 7개 PASS. 서버·모델에 실제 요청하지 않았다.

| 새 연결 검사 | 관측 |
|---|---|
| 첨부 Loki 응답 → 실제 그래프 실행 → 사실/설명 입력 | 원문·서비스·요청 ID 보존, info를 오류 항목으로 표기하지 않음 |
| 성공한 빈 결과 | 설명 단계 도달, 반환 줄 수 0과 오류 필터 범위 표기 |
| 첫 timeout, 다음 성공 | Loki 호출 2회, 두 요청의 범위·필터 동일, 모델 요청 생성 단계 1회 |
| HTTP 503 | Loki 호출 1회, 설명 생략, 종료 코드 2, 오류 0건으로 변환하지 않음 |
| 모델이 다른 서비스를 요청 | 검증 오류, Loki 호출 0회 |

실제 errors-only 쿼리 필터링은 이전 사용자 PC 출력이 근거다. HTTP 대역은 LogQL과 시간 범위를 실행하지 않는다. 실제 Qwen의 요청 생성·설명과 사용자 PC 일반 조회 통합은 아래 후속 출력으로 확인했다.

## 5. 사용자 PC 적용과 실행

수정본 두 파일(local_workflows.py, loki_query.py)을 사용자 PC 프로젝트 루트에 적용한다. 조회 함수에도 prepare_query가 추가됐으므로 두 파일을 함께 갱신한다. 기존 tools_mock.py는 같은 폴더의 의존성으로 사용한다.

```bash
python -u local_workflows.py --model qwen3.5:9b --engine graph --source loki \
  --service order-api --start 2026-10-10T03:48:00Z --end 2026-10-10T03:50:00Z \
  --request-id agent-loki-20261010T034854Z-7943 --limit 20 --summary-style separated
```

이 실행에는 가동 중인 Loki와 Ollama 및 설치된 Qwen 모델이 필요하다. 기존 데이터를 보존하고 있다는 가정이다. 데이터가 사라졌다면 원인을 확인하고 비교 기준을 갱신한다. 빈 결과를 곧바로 에이전트 연결 실패로 단정하지 않는다.

새 서버·패키지·모델 설치를 이 실행의 선행 조건으로 추가하지 않는다. 기존 mock 명령은 기본 source=mock으로 동작한다. Loki에서는 --scenario를 받지 않는다.

## 6. 현재 판단과 남은 범위

### 사용자 PC 실제 실행: 17:16 KST 공유

사용자는 수정본 두 파일을 적용하고 위 명령을 실행했다. 조회 범위는 2026-10-10T03:48:00Z 이상~03:50:00Z 미만, request_id는 agent-loki-20261010T034854Z-7943이었다. 조회 자체는 08:15:49.177401Z(17:15:49 KST)에 실행됐다. 최신 로그를 조회한 사례가 아니라 이전에 확인한 12:48:55 KST 요청을 고정 범위로 재조회한 사례다.

| 최소 관측 위치 | 실제 증거 | 판정 |
|---|---|---|
| request | 함수 get_logs, 인자 service=order-api | 요청 대상 일치 |
| execute | 시도 1/2, source=loki, status=ok, returned_count=1, limit_reached=false | 실제 도구 조회 성공 |
| 코드 사실 | timestamp_ns=1791604135340155505, level=info, 같은 요청 ID/trace_id/원문, 반환 1줄 | 앞선 curl/Python 근거와 일치 |
| 모델 설명 | info 레벨의 성공 응답이라고 설명하고 서비스 전체 정상 여부는 단정할 수 없다고 명시 | 이 입력에서 확인된 사실과 모순 없음 |

모델의 다음 확인 문장은 다른 모니터링 지표·메트릭 확인 제안이다. 이번 실행에서 메트릭을 조회했다는 증거는 아니다. 제안의 대상·시점이 구체적이지는 않지만 원인이나 서비스 전체 상태를 만들어내지 않았다. 설명 상태 ok만으로 평가하지 않고 실제 문장을 대조했다.

| 관측 수치 | 요청 생성 | 설명 |
|---|---:|---:|
| 모델 invoke elapsed_seconds | 6.33 | 1.10 |
| load_seconds | 5.85 | 0.01 |
| 입력 토큰 | 388 | 981 |
| 출력 토큰 | 27 | 63 |
| total_tokens | 415 | 1044 |
| done_reason | stop | stop |

모델 invoke는 2회, 도구 조회는 1회다. 두 모델 호출의 보고 토큰 합계는 1459다. Loki 함수 elapsed_seconds는 0.0362였다. 모델 elapsed에는 적재가 포함되어 있으므로 6.33초 전체를 생성 추론 시간으로 해석하지 않는다. 이 값들은 전체 CLI 시간이나 반복 성능 평가 결과가 아니다.

### 결과에 따른 행동

네 최소 관측이 모두 일치했다. 이 사례의 일반 조회 통합 확인을 종료한다. 같은 입력·설정으로 추가 성공 횟수를 채우지 않는다. 새 연결 코드 수정이 필요한 모순은 이번 출력에서 관측하지 않았다.

미확인 범위: 실제 오류 로그에 대한 통합 설명, 실서버 조회 실패/재시도, 모델 설명의 반복 신뢰성, 자유로운 자연어 입력·시간 추출, 다중 도구 재조사, 전체 실행 예산, 지속 저장·재개. 이 목록을 모두 즉시 실행할 테스트 목록으로 취급하지 않는다. 다음 사용자 요구가 결정되면 그 요구를 구현하고 필요한 새 증거를 선정한다.
