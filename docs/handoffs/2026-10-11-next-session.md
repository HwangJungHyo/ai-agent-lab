## 목적과 안내 원칙

LangChain/LangGraph로 실제 관측 데이터를 조회하는 프로그램을 직접 만들며 실무 설계 판단을 배우는 중이다. 항상 문제 → 왜 필요한가 → 대안과 선택 근거 → 어떻게 확인하는가 → 관측과 한계 → 다음 행동 순서로 설명해줘. 지식이 부족한 나에게 선택부터 요구하지 말고 기본 경로와 갈림길의 근거를 함께 제공해줘. 관련 질문과 명령은 묶어줘.

실험은 다음 결정을 바꾸는 증거만 확보한다. 이미 확인한 Loki 수집·조회와 같은 입력을 이유 없이 반복하지 않는다. 새 코드·요구·모순 때문에 재검증할 때는 변경 조건과 종료 기준부터 정한다. 모델·도구·코드·실제 PC 결과·대역 테스트를 구분하고, 성공 출력만으로 내 이해나 운영 신뢰성을 판정하지 않는다.

## 현재 구현과 확인된 범위

1. Gemini SDK/API, mock 도구 호출, chain/graph 비교, 도구 QUERY_TIMEOUT 최대2회 재시도, 모델 HTTP503 재시도 구분을 실습했다.
2. Qwen/Ollama로 전환했고, 필수 사실은 코드가 출력하고 모델 설명은 별도 영역에 둔다. 모델 설명이 사실 영역을 덮어쓰지 않는다.
3. 실제 Loki 단독 조회와 Qwen+LangGraph 고정 조건 조회를 확인했다. 기존 info 로그1줄의 원문·시각·조회 범위가 보존됐다.
4. 자연어 입구는 --question이다. 모델에는 실행하지 않는 propose_log_query 도구 명세를 제공하고 service/minutes/errors_only/unresolved를 제안하게 한다. 코드가 정규화·검증한 뒤 질문/미리보기/조회로 분기한다. 기본은 미리보기, --run-query가 있어야 실제 조회한다.
5. 모델이 "10"과 "true"/"True" 같은 문자열을 반환한 실제 오류를 관측했다. 숫자 문자열과 true/True/false/False만 제한적으로 정규화한 뒤 1~60분 제한을 검사한다. 대상 추정·누락 보정·범위 축소는 하지 않는다. 원안과 변환 내역은 표시한다.
6. '아까 결제가 이상했어'는 service/minutes/errors_only=null로 대상·시간·증상을 함께 질문했고 조회 없이 종료했다. 명확한 요청의 정규화·미리보기도 실제 PC에서 확인했다.
7. 2026-10-10 23:55 KST 공유 출력에서 자연어→실제 Loki→코드 사실→모델 설명까지 확인했다. 이 연결 실험은 종료했다. 반복 신뢰성·실제 error로그·실서버 실패 전부를 확인했다는 뜻은 아니다.

## 최신 실제 조회와 남은 문제

실행:
python -u local_workflows.py --model qwen3.5:9b --engine graph --source loki --question 'order-api의 최근 10분 오류 로그를 확인해줘' --run-query

관측:
- 모델 제안: service=order-api, minutes="10", errors_only="true", unresolved=[] → 코드 정규화·검증 성공.
- 실제 Loki 조회1회, source=loki, status=ok, 반환0줄, 상한20줄.
- 범위: 2026-10-10T14:44:27.737300Z 이상~14:54:27.737300Z 미만. 실제 조회 시각14:54:27.737818Z.
- LogQL: {service_name="order-api"} | json | __error__="" | level="error"
- 해석 모델4.18초(적재3.10초), 설명 모델1.45초, 토큰671+623=1294. 성능 벤치마크가 아니다.
- 코드가 '이번 조건에서 반환된 로그 없음, 서비스 정상 여부 판단 불가'를 정확히 출력했다.
- 모델은 'limit 설정으로 인해 결과가 누락되었을 가능성'을 언급했다. 0줄<20줄이므로 이 결과에서 상한 누락을 제안할 근거가 없다. 헬스 체크·추가 조회는 제안이며 실제 실행하지 않았다.
- explanation_status=ok는 텍스트 생성 완료이지 의미 정확성 통과가 아니다.

## 다음에 할 일

먼저 구현안을 설명하고 ① 중요한 판단 한계를 코드로 출력하는 보완부터 진행해줘. 다음의 초점은 Loki가 동작하는지 재확인하는 것이 아니라, 모델이 근거 없는 가능성을 덧붙일 범위를 어떻게 줄이는가다.

- 기존 사실 출력은 유지하고, 조회 성공 여부·빈 결과·limit_reached·서비스/수집 상태 미확인 등 검사 가능한 조건을 코드가 계산한다.
- 중요한 판단 한계는 코드로 출력하고 모델은 추가 확인 제안을 맡기는 방식을 기본 경로로 검토한다. 프롬프트 강화만의 대안과 설명 자유도 감소도 설명해줘.
- 이미 확보한 빈 결과를 재사용한다. 고정 입력을 재구성하면 관측값과 코드로 유도한 값, 미제공 값을 구분해 기록한다. 현재까지 원본 tool JSON을 파일로 저장한 것으로 가정하지 않는다.
- 모델의 형식 검사와 의미 정확성을 구분한다. 자유 설명의 의미 정확성을 일반적으로 코드가 보장한다고 주장하지 않는다.
- 최소 기준: 코드가 조회 범위·반환0줄·정상 판정 불가를 유지하고, 모델의 'limit로 인한 빈 결과' 추측이 사용자 보고에 남는지 별도로 평가한다. 표현만 금지하는 검사는 우회 표현까지 보장하지 않는다.
- 코드 정책 검사는 대역으로, 실제 설명은 확보한 고정 결과만으로 확인한다. Loki 재조회·장애 주입은 불필요하다. 필요한 검사만 실행한다.

후속 순서와 이유:
① 근거 통제: 실제로 관측한 설명 오류 보완.
② 승인·중단·재개: 지금은 재실행 때 모델 제안·상대 시간이 달라진다. 승인한 조건을 그대로 저장·실행하기 위해 체크포인트/interrupt/resume을 검토한다.
③ 프로세스 재시작 후 재개: SQLite 등 영속 저장으로 조건 유지·중복 실행 방지 확인.
④ 추가 조사: 서비스 상태 판단 요구가 있으면 로그 외 메트릭 도구를 연결하고 고정 절차와 모델 선택을 비교.
⑤ Langfuse 추적: 모델·검증·조회·보고·실패가 어느 작업에서 발생했는지 추적.
⑥ 평가·개선: 기대 행동·금지 결론을 정한 고정 사례로 품질·시간·비용을 함께 평가.

현재 체크포인트·승인 후 재개·Langfuse·메트릭 조회는 미구현이다. 후속 순서는 제안이며 전부 완료한 것으로 쓰지 않는다. 새 변경의 커밋·푸시는 변경 내용을 보여준 뒤 요청 범위에 맞게 진행해줘.
