# 왜 필요한가 → 그래서 왜 이 선택인가 → 어떻게 확인하는가

작성: 2026-10-08. 사용자 학습 목표를 기준으로 한 저장소 공통 원칙.

## 목적

어떤 구축·시뮬레이션·테스트를 하더라도 중심은 **문제와 선택의 이유를 이해하고, 검증할 방법을 세우며, 결과를 근거로 설명하는 것**이다. 실행과 Git 기록은 그 과정을 돕는다.

지식이 충분하지 않은 학습자에게 설계 선택부터 요구하지 않는다. 안내자는 개념과 기본 구현을 제공하고, 선택지가 생기는 지점에서 추천 이유와 대안의 조건을 함께 설명한다. 학습자는 실물을 만들고 관찰하면서 판단 근거를 쌓는다.

## 매 실습의 흐름

| 질문 | 기록할 내용 | 빠졌을 때 생기는 문제 |
|---|---|---|
| 무엇이 문제인가? | 현재 관찰된 불편·실패와 해결하려는 요구 | 기술을 쓰는 것 자체가 목표가 됨 |
| 왜 확인해야 하는가? | 확인하지 않으면 남는 불확실성과 실무 영향 | 실행 성공 여부만 보게 됨 |
| 그래서 왜 이 방법인가? | 대안, 이번 추천, 가정·비용·한계, 선택을 바꿀 조건 | 특정 도구나 설정을 정답으로 외움 |
| 어떻게 확인할 것인가? | 바꿀 조건·고정 조건·예상 결과·판단 기준 | 결과를 보고 유리하게 기준을 바꿈 |
| 실제로 무엇이 나왔는가? | 실행 명령, 출처, 주요 로그와 수치 | 주장과 관측 사실이 섞임 |
| 그래서 무엇을 알게 됐는가? | 가설 지지·반박·판단 보류와 미확인 범위 | 일부 성공을 전체 성공으로 확대함 |
| 다음에는 왜 무엇을 하는가? | 남은 질문과 그것을 줄일 다음 행동 | 목적 없이 다음 기술로 넘어감 |

이 흐름은 설명 순서다. 간단한 수정마다 긴 보고서를 만들거나 학습자에게 일곱 질문을 먼저 답하게 하는 절차가 아니다. 중요도가 낮은 구현 세부사항은 묶어 설명한다.

## 선택을 설명하는 방식

추천을 할 때는 다음 네 항목이 연결되어야 한다.

1. **조건:** 무엇을 만들고 어떤 제약을 지키는가?
2. **선택:** 이번에는 무엇을 사용하는가?
3. **근거와 대가:** 조건에 왜 맞고 무엇을 더 관리해야 하는가?
4. **변경 조건:** 어떤 요구가 생기면 다른 선택을 하는가?

예: 같은 로그 조회 요청을 일시 실패 후 다시 시도하는 실습에서는 저장한 요청으로 도구만 재실행한다. 원래 질문과 대상이 변하지 않았으므로 요청 생성 모델을 다시 호출할 필요가 없기 때문이다. 반면 새로운 증거 때문에 조사 대상부터 바꿔야 한다면 모델의 재계획이 필요할 수 있다.

## 기록의 단위와 역할

원칙적으로 **실험 기록 하나는 답하려는 핵심 질문 하나**를 중심으로 쓴다. 관련 케이스 여러 개는 하나의 표에서 비교한다. 같은 날짜라는 이유만으로 서로 다른 문제를 계속 이어 붙이지 않는다.

| 문서 | 역할 |
|---|---|
| README.md | 현재 목적과 주요 문서로 가는 입구 |
| docs/learning-principles.md | 학습·설명·판단의 공통 원칙, 내용의 기준 문서 |
| AGENTS.md | 저장소 작업 시 위 원칙을 적용하도록 하는 짧은 지침 |
| docs/progress.md | 확인 완료·부분 진행·미확인 항목과 다음 질문 |
| docs/evidence/TEMPLATE.md | 새 실험을 같은 사고 흐름으로 기록하는 양식 |
| docs/evidence/실험기록.md | 질문·선택·예상·관측·해석을 연결한 근거 |
| examples/ | 코드와 실행법; 검증 사실은 증거 문서로 연결 |

이전 일일 기록은 회고·색인으로 유지해도 된다. 이후 큰 결정이나 다른 질문이 생길 때 실험 문서를 나눈다. 필요가 커지기 전에는 결정 로그·용어집·주간 보고서를 각각 추가하지 않는다.

## 증거와 완료 기준

- 실행 전 예상과 실행 후 실제 결과를 같은 항목으로 비교한다.
- 사후에 정리한 가설·이유·판단 기준은 사후 정리라고 밝힌다. 학습자가 당시 이미 이해·선택했다고 꾸미지 않는다.
- 모델 응답, 프로그램 제어 흐름, 실제 운영 환경 검증을 구분한다.
- 테스트 성공은 해당 입력·환경·조건에서의 결과다. 반복 신뢰성이나 모든 실패 처리를 보장하지 않는다.
- 외부 장애로 목표 단계에 도달하지 못한 경우, 그 단계의 가설은 실패가 아니라 미검증일 수 있다.
- 사용자가 설명하지 않은 내용은 이해 확인 완료로 표시하지 않는다. 안내자가 선택한 구현 이유와 학습자가 직접 설명한 내용을 구분한다.
- 변경안을 검토받은 후 승인 범위에 따라 커밋·푸시한다.

## 다음 행동을 결정하는 최소 증거

2026-10-10 추가. 실험 전에 **결과 A이면 무엇을 하고, 결과 B이면 무엇을 다르게 하는가**를 적는다. 결과가 다음 선택이나 수정에 영향을 주지 않으면 필수 선행 실험으로 두지 않는다. 학습을 위해 원리를 관찰하는 실험은 학습 목적과 확인할 차이를 따로 명시한다.

새 실험의 필수 기록은 다음 다섯 가지다. 더 상세한 기록은 실패 원인을 설명하거나 결과를 재현할 때 필요한 항목만 추가한다.

| 항목 | 남길 내용 |
|---|---|
| 결정할 질문 | 한 문장. 어느 코드·설계·요구를 결정하는가? |
| 이미 있는 근거 | 기존 기록 링크, 검증된 코드·설정·입력·환경 범위 |
| 새로 바뀐 조건 | 이전 검증으로 설명되지 않는 변경 또는 남은 구체적 불확실성 |
| 최소 관측과 종료 기준 | 어느 값·경로를 보면 다음 행동을 정할 수 있는가? 확인되면 중단 |
| 결과별 행동 | 예상 일치 시 다음 단계, 불일치 시 확인·수정할 위치 |

재실행은 (1) 관련 코드·설정·계약·환경이 변경됨, (2) 이전 근거와 모순되는 새 결과가 나옴, (3) 기존 검증 범위 밖의 요구를 구현해야 함, (4) 반복 신뢰성·성능을 평가하기 위한 사전 계획이 있음 중 하나가 있을 때 한다. 실행이 실패했다면 근거·조건을 먼저 확인하고 필요한 부분만 다시 실행한다. 날짜가 바뀌었거나 기록을 채우기 위한 이유만으로 같은 실험을 반복하지 않는다.

오픈소스 제품 전체의 동작을 다시 입증하려는 실험보다 우리가 작성한 연결·변환·권한·실패 정책의 요구를 확인하는 실험을 우선한다. 다만 실제 배포·운영 요구가 관련 환경의 검증을 필요로 하면 그 요구에 맞는 종단 검증을 수행한다. 단위 테스트·대역 테스트를 실제 환경의 증거로 바꾸어 기록하지 않는다.

예: 앱 → Loki → Python 조회는 이미 같은 요청 ID로 확인했다. LangGraph 연결 후에는 그 경로 자체를 반복 검증하기보다 **새 도구 호출·상태 전달·사실 출력·설명 입력**을 확인한다. 기존 로그 1줄의 원문·시각·요청 ID를 비교 기준으로 재사용한다. 이는 같은 조회를 포함하지만 새로 바꾼 에이전트 연결을 검사하는 실행이다.

## 다른 대화에서도 사용할 공통 지침 문구

> 어떤 구축·시뮬레이션·테스트에서도 ‘왜 필요한가 → 그래서 왜 이 방법인가 → 어떻게 확인할 것인가’를 중심으로 안내해 주세요. 먼저 필요한 개념과 기본 구현 경로를 제시하고, 주요 선택지의 장단점·추천 근거·선택을 바꿀 조건을 설명해 주세요. 실행 전에는 예상과 판단 기준, 실행 후에는 관측 사실·해석·한계·다음 행동의 이유를 연결해 주세요. 지식이 없는 상태에서 선택부터 요구하거나, 성공 로그만으로 학습 완료를 판단하지 마세요. 관련 설명과 명령은 한 묶음으로 주세요.

이 문구는 일반 대화의 사용자 지정 지침이나 프로젝트 지침에 옮겨 사용할 수 있다. 저장소 문서를 추가한 것만으로 해당 설정을 변경한 것은 아니다.
